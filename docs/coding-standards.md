# コーディング規約

GutenbergReader のコードを書くときの約束をまとめる。目的は 2 つある。

- **品質**: 壊れにくく、失敗したときに理由が分かり、Windows でも Linux でも同じように動くこと。
- **コンテキスト節約**: 人も AI エージェント（Claude Code など）も、必要なファイルだけを少し読めば変更できること。読む量が減ると、見落としも減る。

全プロジェクト共通の指示（`~/.claude/CLAUDE.md`）を前提にし、ここではこのプロジェクトに固有の約束を書く。テストの書き方の詳細は [testing.md](testing.md) にある。

## 1. 品質の規約

### 1.1 型

- `any` を使わない。型が決まらない値は `unknown` で受け、`instanceof` や `typeof` で絞り込んでから使う（例: `reader.component.ts` の `errorText`）。
- 型を広げずに形だけ確かめたいときは `satisfies` を使う。テストの偽物にも使い、本物の型が変わったら偽物のビルドが失敗するようにする。
- 「成功か失敗か」を返す関数は、例外ではなく判別できる型にする（例: `{ ok: true; path: string } | { ok: false; message: string }`）。プロセスや IPC をまたぐ戻り値は必ずこの形にする。
- `null` は「値がない」ことを表すのに使い、`undefined` と混ぜない。戻り値の型の JSDoc に、`null` が何を意味するかを書く（例: 「キャンセルなら null」）。
- `tsconfig.json` の `"strict": true` を外さない。

### 1.2 構成と責務

処理は次の 3 層に分け、外側ほど薄くする。

| 層         | 置き場所                                                                                     | 書くもの                                                           | テスト                                            |
| ---------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------- |
| 純粋な関数 | `src/app/services/*.ts`（`Service` が付かないファイル）、`electron/*.mjs`（`main.mjs` 以外） | 解析・整形・判定・計算。DOM・通信・ファイル・時刻に触れない        | 関数単位で、入力と出力だけを確かめる              |
| サービス   | `src/app/services/*.service.ts`                                                              | 外とのやり取り（HTTP・Electron の API）と、その結果の受け渡し      | TestBed で外を偽物に差し替える                    |
| 画面・入口 | `src/app/components/`、`electron/main.mjs`、`electron/preload.cjs`                           | 画面の状態と操作、Electron の API の呼び出し。判断は下の層に任せる | 画面は操作ごとに。`main.mjs` は自動テストの対象外 |

- 新しい判断（「この値なら許す」「この形式なら読む」など）は、まず純粋な関数として書く。コンポーネントや `main.mjs` に直接書かない。
- `electron/main.mjs` は Electron の中でしか動かずテストできない。中に `if` を増やしたくなったら、`paths.mjs`・`log-file.mjs` のように別の `.mjs` に切り出す。
- `src/app/pstudy/` はサブモジュール `pstudy-dict/` からの自動コピーなので編集しない。直すときは `pstudy-dict` 側で直す。

### 1.3 Angular

- コンポーネントは standalone にする。依存は `inject()` で受け取る（コンストラクタ引数にしない）。
- 状態は `signal` と `computed` で持つ。外に見せる状態は `asReadonly()` で読み取り専用にする（例: `ReadingLogService.logPath`）。
- テンプレートの制御は `@if`・`@for`（`track` 必須）を使い、`*ngIf`・`*ngFor` は使わない。仮想スクロールの `*cdkVirtualFor` は例外とする。
- Observable は `firstValueFrom` で Promise にして `await` する。コンポーネントで `subscribe` しない（購読の解除漏れを防ぎ、テストで完了を待てるようにする）。
- 非同期のメソッドは `void` ではなく `Promise<void>` を返す（テストで完了を待つため）。
- テンプレートからだけ使うメンバーは `protected` にする。外から使わせたい操作だけを `public` にする。
- 連打されると困る操作（記録など）は、処理中フラグの `signal` で 2 回目を止め、ボタンも `disabled` にする。

### 1.4 エラー処理

- エラーを握りつぶさない。`catch` したら、画面に理由を出すか、意味の分かるエラーに包み直して投げる。空の `catch {}` は書かない（壊れた入力を「なし」とみなす場合だけ許し、その理由をコメントに書く）。
- 呼び出し側が区別したい失敗には、専用の `Error` のサブクラスを作る（例: `BookFetchError`・`LogPathNotSetError`・`LogWriteError`）。
- 画面に出すメッセージは日本語で、**何ができなかったか**と**どうすればよいか**を書く（例: 「記録ファイルが UTF-8 ではないため読み書きしませんでした。…「CSV UTF-8（コンマ区切り）」で保存してください」）。英語の生のエラーメッセージをそのまま出さない。
- 一部が壊れていても続けられるなら続け、壊れた所を知らせる（例: 記録 CSV の読めない行は飛ばし、行番号を表示する）。
- 外部サイトへの接続の失敗は、例外ではなく理由付きの応答（502 など）にして画面まで届ける。

### 1.5 安全

- 画面（レンダラー）からの要求は、乗っ取られた画面から来るものとみなして入口で絞り込む。IPC を足すときは次を必ず行う。
  - 呼び出し元を `isFromApp` で確かめる。
  - 引数の型（`typeof`・`instanceof`）を確かめる。
  - ファイルのパスは `isCsvPath` のように、読み書きしてよい範囲に限る。
  - 失敗は `{ ok: false, message }` で返す。
- 画面に公開する API は `preload.cjs` の `gutenbergDesktop` の 1 か所だけにし、型を `desktop-bridge.service.ts` の `GutenbergDesktop` とそろえる。
- 外部から取った文字列（本文・Weblio の結果）を HTML として埋め込まない。テンプレートの補間（`{{ }}`）で表示する。

### 1.6 Windows と Linux

- パスは `node:path` の `join`・`resolve`・`extname` で扱い、`/` や `\` を文字列でつながない。テストのパスも同じ方法で組み立てる。
- 記録 CSV は UTF-8（BOM 付き）・改行 CRLF で書く。読むときは `\r?\n` で分け、どちらの改行でも読めるようにする。
- npm スクリプトに OS 固有のコマンド（`rm`・`cp`・`&&` に頼る書き方など）を書かない。必要なら `scripts/*.mjs` に Node で書く。

### 1.7 画面の文言とアクセシビリティ

- 画面の文言は日本語で書く。半角カナは使わない。
- ボタンや入力欄には、目に見える名前を付ける。アイコンだけのボタン（`×` など）には、何を対象にするかを含む `aria-label` を付ける（例: 「apple を削除」）。
- 状態（範囲の開始行・終了行など）を色だけで表さない。文字や `aria-*` でも伝える。
- マウスでしかできない操作を作らない。ダブルクリックなどには、キーボードでの代わりの操作を用意する。
- 文字色は背景とのコントラスト比 4.5:1 以上にする。

### 1.8 整形と書き方

- 保存の前に Prettier で整形する（`npx prettier --write <ファイル>`）。設定は `.prettierrc`（1 行 100 文字・シングルクォート）。
- `npm run lint`（ESLint）でエラーを 0 にする。設定は `eslint.config.js`（TypeScript・テンプレートのアクセシビリティ・Electron の Node 向け）。ルールを外すときは、外す範囲を最小にし、理由をコメントに書く。
- 目に見えない文字（BOM など）をそのまま書かず、`'\uFEFF'` のようにエスケープで書く。
- 名前は英語で付け、コメントは日本語で書く。
- コメントには「何をしているか」ではなく「なぜそうするか」を書く（例: 「ignoreBOM: true で BOM を文字として残す（画面側の parseLog が取り除く）」）。
- 魔法の数値に名前を付ける。CSS と TypeScript で値をそろえる必要があるときは、両方にそのことを書く（例: `LINE_HEIGHT` と `.line` の高さ）。
- テストを先に書き、失敗することを確かめてから実装する。詳細は [testing.md](testing.md)。

## 2. コンテキスト節約の規約

### 2.1 ファイルの大きさと分け方

- 1 ファイルは 1 つの責務にし、**ソースは 300 行、テストは 400 行**を目安に分ける。超えそうなら、責務ごとにファイルを分ける。
  - 例: 読書画面のテストは操作ごとに `reader.open.spec.ts`・`reader.record.spec.ts` などに分け、共通のデータを `reader.testing.ts` に置いている。
  - `reader.component.ts`（264 行）にこれ以上の判断を足すときは、純粋な関数として `services/` に出す。
- ファイル名だけで中身が分かるようにする。`utils.ts`・`helpers.ts`・`common.ts` のような何でも入る名前を作らない。
- 純粋な関数のファイルとそのテストは同じフォルダに並べる（`text-count.ts` と `text-count.spec.ts`）。

### 2.2 ファイルの先頭と公開する関数

- Electron 側（`.mjs`・`.cjs`）のファイルの先頭 1〜2 行に、役割と、どこから使うか・テストはどこかを書く。`head -3` で中身の見当がつくようにする。

  ```js
  // 外部サイト（Gutenberg・Weblio）への中継（electron/main.mjs から使う。テストは relay.test.mjs）
  ```

- `export` する関数・クラスには 1 行の JSDoc を付け、引数の単位や、`null` が何を意味するかを書く。中身を読まなくても使えるようにする。
- 型の定義は 1 か所に置き、ほかでは `import` する（例: `GutenbergDesktop`・`ReadingRecord`）。同じ形を別の所で書き直さない。

### 2.3 読まなくてよいものを決めておく

次は生成物か外部のもので、調べものの対象から外す。検索するときも除外する。

| 場所                                  | 理由                                                                                   |
| ------------------------------------- | -------------------------------------------------------------------------------------- |
| `node_modules/`・`.angular/`・`dist/` | 依存とビルドの結果                                                                     |
| `src/app/pstudy/`                     | `pstudy-dict` からの自動コピー（元はサブモジュールの `pstudy-dict/src/app/services/`） |
| `package-lock.json`                   | 依存の固定。依存を変えるとき以外は読まない                                             |

```sh
grep -rn "parseLog" src electron --include=*.ts --include=*.mjs --exclude-dir=pstudy
```

### 2.4 索引と記録を最新に保つ

- **README の「プログラムの構造」の表を、ファイルの索引にする。** ファイルを足す・消す・役割を変えるときは、同じ変更で表も直す。ここを読めば、どのファイルを開けばよいかが分かるようにする。
- 重要な決定（仕様の解釈、見送ったこと、方式の変更）は `docs/superpowers/2026-11-03-implementation-log.md` に **1 行**で追記する。「何を決めたか — 理由 — 誤りだった場合の影響」の順に書く。
- 同じことを 2 か所に書かない。使い方は README、テストは `docs/testing.md`、規約はこのファイル、と置き場所を分け、ほかからはリンクする。
- プロジェクトの `CLAUDE.md` は毎回自動で読み込まれるので、30 行以内の要点と、このファイルへのリンクだけにする。詳しいことはここに書く。

### 2.5 コマンドの出力を絞る

- テストの結果は、件数と失敗した所だけを見る。全体を流すのは失敗の原因を調べるときだけにする。

  ```sh
  npm test -- --watch=false 2>&1 | grep -E "Test Files|Tests |FAIL|×"
  npm run test:electron 2>&1 | grep -E "Test Files|Tests |FAIL"
  ```

- 大きいファイルは全体を開かず、`grep -n` で場所を見つけてから、その前後だけを読む。

### 2.6 変更を小さくする

- 1 回の変更では 1 つの目的だけを扱う。ついでの整形や名前の変更を混ぜない（差分を読む量が増え、見直しで見落とす）。
- 今回変更しないファイルの整形はしない。Prettier をかけるのは変更したファイルだけにする。

## 3. 変更するときの確認

変更を終える前に、次を確かめる。

- [ ] テストを先に書き、失敗→成功を確かめた
- [ ] `npm test -- --watch=false` と `npm run test:electron` が通る
- [ ] 変更したファイルを Prettier で整形し、`npm run lint` が通る
- [ ] エラーの場合を握りつぶさず、日本語の理由を画面に出している
- [ ] パスを `node:path` で扱い、Windows でも動く
- [ ] IPC を足したなら、入口の確認（呼び出し元・型・パスの範囲）をした
- [ ] ファイルを足した・役割を変えたなら、README の構造の表を直した
- [ ] 外から見える動きが変わったなら、README の使い方を直した
- [ ] 重要な決定を実装記録に 1 行で書いた
